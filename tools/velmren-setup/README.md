# Velmren Windows setup

Native, per-user WinForms frontend for the delivery engine. Build with the .NET 10 SDK and the .NET Framework 4.7.2 reference pack. The single EXE uses Windows' included .NET Framework: 4.7.2 on Windows 10 1809, 4.8 on Windows 10 1903 and later, and 4.8/4.8.1 on Windows 11. Users do not install or download another runtime. See Microsoft's [Windows/framework version table](https://learn.microsoft.com/en-us/dotnet/framework/install/on-windows-and-server). The browser's root launcher remains a separate, uncompressed .NET 10 executable; this change does not add WinForms or framework initialization to browser startup. Setup does not request elevation, make itself the default browser, or expose delivery configuration in the install window.

The release's main `setup/VelmrenSetup.exe` is the online installer and downloads the browser from its embedded HTTPS feed. `offline-setup/VelmrenSetup.exe` is the optional full package for installation without a download. Both use the same UI and signed-package verification contract.

```powershell
# First build maintenance, then place it in the signed payload inventory.
.\Build-Setup.ps1 -EnginePath C:\build\Velmren.exe -OutputDirectory C:\build\maintenance

# After packaging the signed payload, create an offline setup.
.\Build-Setup.ps1 -EnginePath C:\build\Velmren.exe -BundleDirectory C:\build\bundle -OutputDirectory C:\build\setup

# Online installer; an offline bundle remains available for installation without a download.
.\Build-Setup.ps1 -EnginePath C:\build\Velmren.exe -Feed https://updates.example/velmren/preview/win-x64/ -OutputDirectory C:\build\setup
```

`BundleDirectory` must contain `manifest.json` (the delivery engine's signed envelope) and the ZIP named by its decoded payload. That ZIP must contain exactly one `delivery/Velmren.exe`, byte-identical to `EnginePath`. The build script checks the engine SHA-256 and size but does not establish manifest trust. The delivery engine still verifies the pinned signature and complete package inventory before installation. There is no private-key input. Sign the final output with the real release Authenticode identity in the release pipeline; this script does not create a certificate or alter Windows trust settings.

The default output is `VelmrenSetup.exe` when a bundle/feed is supplied and `VelmrenMaintenance.exe` otherwise. `-Name`, `-Runtime` (`win-x64` or `win-arm64`), and `-Version` may be specified. The matching architecture engine must already be a self-contained single EXE. Intermediate build inputs and output are retained under `OutputDirectory/build-*` for inspection.

The UI assembly is AnyCPU with 32-bit preference disabled. Windows 11 on ARM uses its ARM64-capable .NET Framework 4.8.1; Windows 10 on ARM is not part of the verified setup baseline. `Runtime` describes the supplied engine, not an extra UI runtime payload.

| Artifact | Embedded payload resources | Engine source |
| --- | --- | --- |
| Maintenance | `Setup.Payload.Config` | Copy installed `ROOT/Velmren.exe` to the invocation's private cache and verify pinned SHA-256/size before execution; after an update, try the same pinned engine in a retained version. |
| Online Setup | Config and `Setup.Payload.Engine` | Engine resource is gzip-compressed; decompress and verify before execution. |
| Offline Setup | Config, `Setup.Payload.Manifest`, `Setup.Payload.Package` | Reuse `delivery/Velmren.exe` inside the canonical ZIP and verify before execution; no duplicate embedded engine. |

Generated config has `Feed` (HTTPS string or null), `Package` (ZIP filename or null), `EngineSha256` (64 lowercase hex characters), `EngineSize` (positive byte length, at most 512 MiB), and `EngineSource` (`installed`, `gzip`, or `package`). Maintenance rejects feed/package inputs. `.build.json` records `uiFramework`, `engineSource`, and `engineSha256` in addition to the existing artifact fields. The `Build-ReleaseBundle.ps1` invocation and output-filename contract is unchanged.

Framework high-DPI configuration is written only to an ACL-private invocation directory and selected before WinForms/configuration initialization. It enables [PerMonitorV2 and dynamic scaling](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/high-dpi-support-in-windows-forms?view=netframeworkdesktop-4.8), then is removed on exit. No adjacent `.config` or DLL needs to be shipped with the EXE. The modern Explorer folder picker uses the Windows [IFileDialog interface](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-ifiledialog).

## Engine contract

Every awaited command receives `--cancel-file PATH`; the path belongs to this setup invocation. On cancellation, the frontend creates that file and waits up to eight seconds before terminating only its engine process. It never kills a process tree. The engine owns transactional installation, recovery, trust checks, path validation, running-process checks, and registration rollback.

- Offline: `install-bundle --root ROOT --bundle-directory DIR [--feed HTTPS]`
- Online: `install --root ROOT --feed HTTPS`
- After successful installation: `register --root ROOT --desktop true|false`
- Removal: `uninstall --root ROOT`, preserving browser profile and agent state
- Open Velmren: starts installed `ROOT/Velmren.exe launch --root ROOT`, detached from setup; Close exits without launching

Arguments use the Windows CRT quoting rules with `ProcessStartInfo.Arguments`, never a shell. The engine streams one JSON object per line on stdout: `{"action":"extracting","percent":40,"completed":400000000,"total":1000000000}`. `action` is required; integer `percent` is optional and clamped to 0–100. Download and extraction counters are bytes; `verifying-files` counters are files. `phase-started` and `phase-completed` include a known `phase` and optional `elapsedMs`, `version`, `bytes`, `files`, and `succeeded` metadata. The parser accepts integer counters up to 1 TiB, file counts up to 10 million, and elapsed milliseconds up to `Int32.MaxValue`; it rejects negative, fractional, string, and inconsistent counters. Null metadata remains optional. Unknown phases and unrecognized output are ignored. stderr is captured with an 8 KiB limit and mapped to concise user-facing recovery guidance. The engine's own journal is authoritative for diagnostic details. The UI does not display raw feed URLs, certificates, keys, exceptions, or signed-manifest internals.

The maintenance command is `VelmrenMaintenance.exe --uninstall --root ROOT`. Its initial window asks the user to confirm removal and explains that saved data remains. There is no delete-profile option. With no package/feed, an explicit `--root`, and an installed `ROOT/Velmren.exe`, the same file opens maintenance/removal. Without an installed root it explains that the full installer is needed.

When invoked for removal from inside the installation tree, maintenance first copies its own executable into an ACL-private cache and restarts that exact copy. The original exits before the copy shows a window, releasing the installed maintenance file for deletion. The internal marker accepts only a canonical GUID, the exact expected copy path, and the matching root record; there is no arbitrary executable-path option. The running maintenance copy is retained in its private cache after exit because it cannot delete its own image. No shell deletion command or global cleanup registration is created. The separate extracted engine/bundle session is cleaned with a bounded asynchronous retry. A cache outside the chosen install root is required.

If an update changes or temporarily removes the root launcher while maintenance is open, maintenance may reuse the matching engine at `ROOT/versions/MAJOR.MINOR.BUILD.REVISION/app/delivery/Velmren.exe`. It inspects at most 64 top-level version entries, accepts only canonical numeric version folders, rejects reparse points along every candidate path, and verifies the same embedded size/SHA-256 before executing a private copy. Cancellation, access, and sharing failures propagate; only missing files or identity mismatches trigger fallback. A different or missing retained engine is never executed.

## Interface

The audience is someone installing or removing a browser in their Windows account. The main path is review the folder → download and install → open Velmren. Offline builds use the same screen with an install action and no download promise. The selected folder is always shown; “Изменить” expands folder editing, the native folder picker, and the optional desktop shortcut. There is no Next/Back wizard. The default folder is `%LOCALAPPDATA%/Programs/Velmren`. Completion has a direct “Открыть Velmren” action and a secondary Close that does not launch anything. The recovery path is cancel/error → retry; removal is confirm → remove → close, with profile preservation stated before and after removal.

The 600×380 initial window uses the existing Velmren V artwork, Segoe UI typography, a neutral surface, and dark teal `#092C35`. Expanded settings increase its height to 460. The primary button and folder field have rounded surfaces; secondary actions are quiet. Button and TextBox subclasses retain Windows keyboard/accessibility semantics instead of reimplementing text entry or button activation. System colors replace branded colors in high contrast. Access keys, Enter/Escape, focus indicators and per-monitor DPI scaling remain available. The layout can resize and scroll; there is no decorative animation or additional UI runtime dependency.

`SetupControls.cs` replaces the classic caption with a minimal drag area and an accessible Close button. Native hit testing supplies dragging and edge/corner resizing, including negative monitor coordinates. Alt+F4 and the Close button use the same form-close lifecycle: a running operation is cancelled and awaited before the window exits. Windows 11 receives the [DWM rounded-corner hint](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/ui/apply-rounded-corners); corner clipping and shadows remain OS-managed, with a rectangular fallback on older Windows. The [custom-frame pattern](https://learn.microsoft.com/en-us/windows/win32/dwm/customframe) keeps native sizing/system-menu styles without drawing a classic caption. No transparency layers, window regions, or separate shadow windows are used.

Progress stays on the UI thread via `Progress<T>`. Embedded package copying, engine decompression, and engine SHA-256 verification run on a worker thread. Preparation reports actual bytes copied, throttled to at most ten intermediate updates per second, plus initial and final reports. The existing identity and private-cache checks still run before any engine execution.

The stage and its actual engine percentage are shown together; byte counters appear below the bar as megabytes copied/downloaded out of the total, and file verification shows checked files out of the total. A percentage can also be calculated from valid counters. Stages without measurements use native indeterminate progress and never an estimated completion promise. Package authenticity, package inspection, extraction, protection setup, file verification, launch readiness, activation, shortcuts, and final cleanup have separate Russian labels. Phase-completion events retain diagnostics but do not alter the current display, since an enclosing phase may finish after a more specific phase has reported progress. Inputs become unavailable while work is running and recover after cancellation/failure. Unknown engine actions do not change the displayed progress.

The structure follows the simplified consumer paths documented by [Chrome](https://support.google.com/chrome/answer/95346?hl=en) and [Firefox](https://support.mozilla.org/en-US/kb/how-install-firefox-windows), reviewed 2026-11-02. Firefox explicitly distinguishes its [full offline custom wizard](https://support.mozilla.org/en-US/kb/custom-installation-firefox-on-windows) from the online installer, which has no folder choice. Velmren keeps the requested folder choice through progressive disclosure; that is our product decision, not a claim that all browser installers offer it. [Brave's official download page](https://brave.com/download/) likewise prioritizes one Get Brave action. These references inform flow and hierarchy; no third-party artwork or installer code is copied.

## Verification

`tests/Run-Smoke.ps1 -OutputDirectory C:\qa\setup` builds a fake engine and all three artifact types, runs process/argument/cancellation/error tests on .NET Framework, and renders the native initial/install and removal forms using offscreen windows with `WS_EX_NOACTIVATE`. It checks gzip extraction, absence of an embedded maintenance engine, cached execution after the original engine is removed, same-size engine substitution rejection, and cleanup. `tests/Test-BuildInputs.ps1` additionally rejects invalid feeds, package paths, and missing/duplicate/mismatched offline engine entries. These renders are layout evidence, not a claim of completed screen-reader, real desktop, or cross-monitor testing. The test engine never installs or registers software. Root-level acceptance must also exercise the final signed-bundle engine and actual maintenance registration.

For UI-only verification, `dotnet run --project tests/Setup.Smoke.csproj -c Release -- C:\qa\setup-ui --render-only` skips all engine/process tests. It renders offline, online, expanded settings, download, embedded package preparation, extraction, file verification, package authenticity verification, retry, success, removal, and simulated 150% layout with larger body text. It checks real disclosure controls, preserved folder edits, measured percentages/counters, stable progress through nested phase completion, action availability, fit, Enter/Escape contracts, Alt+F4, caption-close cancellation, keyboard reachability, native drag/resize hit tests at negative screen coordinates, and unchanged foreground window. The native progress bar's animated fill and DWM corners/shadow are not captured reliably by offscreen `DrawToBitmap`; percentage text and control value are checked separately. Actual pointer dragging, monitor DPI changes, high-contrast switching, and screen-reader output still require desktop acceptance. Do not treat UI-only renders as evidence of installation or registration success.

On 2026-11-02, the progress update passed 372 process/UI checks, 22 maintenance payload checks, and 8 online payload checks, using only the fake engine. Coverage includes bounded 64-bit counters, phase diagnostics, measured preparation on a worker thread, CRT argument quoting, both native frame-layout message forms, modal enable-cycle bounds, and the OS-reported PerMonitorV2 context after form creation. The build-input suite separately covers 12 rejected inputs. Real release byte counts depend on the final engine and package and are recorded by the release builder.
